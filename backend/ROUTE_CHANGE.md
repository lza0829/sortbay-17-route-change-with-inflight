# 改路由表口径（全局唯一）

> 只覆盖“有已路由未封袋件时改路由表”。装载快照贯穿另立需求，不在此处。

## 选定架构：改表强制回流在途

有在途已路由件时**允许改表**，并在**同一笔写事务**内把受影响件强制标错分回流。
另一方案“有在途则拒绝改表”未采用；两者不得混用。

理由：装载条码目的地后，路由表必须能纠正错误映射而不必等所有件封袋；
但纠正必须在同一笔事务里把在途件从旧口门摘走，否则会留下“表已改、在途仍挂旧口”。

## 一次改表的原子动作（`services/routing.py: change_route_mapping`）

在 `BEGIN IMMEDIATE` 事务内：

1. 校验口门存在；
2. 读出受影响集合 = `scans.dest_code = 目的地` 且 `status ∈ {已路由, 已入袋}`；
3. 写 `route_rules` 新映射；
4. 按班次建 `divert_batches`（码 `改表回流-…`）；对每件：
   `status=错分回流`、`bag_id=NULL`、`chute_id=NULL`、挂批次，
   写一条 `route_events`（action=`改表强制回流`，chute_id=旧口门，可追溯）；
5. 写 `route_change_receipts` 回执（含旧/新口门、逐件 from/to、批次），payload JSON 可重放；
6. 写 `audit_events`（action=`改路由并强制回流`）。

任一步抛错 → 整笔 ROLLBACK：路由表与在途都不变，不产生半截、不产生双终态。

### 为什么清空 `chute_id`
回流的件物理上已离开原口门。若保留 `chute_id`，口门页/总览的“在口件数”
（`status ∈ {已路由,已入袋}`）会把回流件算在老口门上。旧口门历史保留在
`route_events` 与回执 payload 中。

## 读路径口径（必须一致）

| 面 | 口径 |
|---|---|
| 路由表 | `route_rules` 当前映射 |
| 在途已路由集合 | `status ∈ {已路由,已入袋}`（= 已路由未封袋） |
| 口门在口 | 同集合按 `chute_id` 计数；回流件不计 |
| 总览 | 分布按 status；口门在口同左 |
| 扫描册/封袋页 | 直接展示 `scans.status` / `chute_id` |
| 审计/回执 | `audit_events` + `route_change_receipts` |

因改表与回流同笔提交，上述各面不会出现“表已改但某面仍旧”的瞬时不一致。

## 并发

所有写路径（改表、封袋开袋/入袋/封口、扫描/路由、回流、口门开闭、班次…）
统一用 `db(write=True)` → `BEGIN IMMEDIATE`，在事务起点取写锁，严格串行。
改表与封袋并发只有两种结局，且都可对账：

- **改表先**：件被强制回流、袋内变空 → 随后的封口因空袋失败（400），终态 `错分回流`；
- **封袋先**：件已 `已封袋`（不再是在途集合）→ 改表不回流它，终态 `已封袋`。

不会出现“已封袋且同时被强制回流”。夹具 `test_concurrent_route_change_and_seal_no_double_terminal`
以 `route_events` 实际动作判定分支，并显式反断言双终态。

## 臂内策略（实现自洽，不跨臂混用）

设置 `回流自动再路由 = 是` 时，强制回流后**同一笔内**再按新映射裁决为新口门的
`已路由`（写第二条 `route_events` action=`改表自动再路由`，回执 `auto_reroute=true`）。
关闭时终态停在 `错分回流`，等待人工/后续再路由。

## 夹具清单（`backend/tests/test_route_change.py`）

1. 有在途改表 → 强制回流、口门/总览/审计/回执同刷；
2. 无在途改表 → 不建批次、`forced_count=0`；
3. 在未封袋内（已入袋）的件同样被强制回流、脱袋；
4. 已封袋件不受影响；
5. 半截故障 → 路由表与在途整笔回滚（无新回执/批次）；
6. 改表与封袋并发 → 只有 A/B 两结局，无双终态；
7. 连续改表 → 无残留旧口门在途件；
8. 强制回流逐件留 `route_events`（不得“强制回流无事件”）；
9. 开启自动再路由 → 臂内终态与回执自洽。

运行：`cd backend && python3 -m pytest tests -q`（夹具库放 `/dev/shm` 以避免 WSL2 fsync 拖慢）。
